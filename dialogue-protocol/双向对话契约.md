# B.1 双向对话契约 v1

对话契约以 `dialogueVersion: 1` 标识，沿用 A.1 已配对的设备、项目和原始需求消息 ID。A.1 的 `message.receipt` 只证明电脑已持久化输入。A.1 的 `user.confirmation`、`user.answer` 以及对话拉取和回执均没有规格授权效力。B.1 提供 Schema、两端校验器和夹具，B.3 实现认证传输与事件持久化。

## 信封与关联

- 每个信封包含 `type`、`dialogueVersion`、`deviceId`、`projectId` 和 `sessionId`。首次开启会话的 A.1 `user.message` 的消息 UUID 同时作为 `sessionId`。手机在收到 A.1 回执后可对该会话重试查询。会话排队、后续消息归属由 B.3 事务管理。
- 每个事件还带 `eventId`、`sequence`、`createdAt` 和 `messageId`。`messageId` 是触发当前规格回合的 A.1 需求，两个方向各维护一条从 1 开始的连续序列。所有 ID 和游标按设备、项目、会话隔离。
- `desktop.question` 携带问题正文、有效期和当前草案的 `specVersion/specSha256`。该事件 ID 即问题 ID。每次有一个可回答的问题。下一问题通过新事件发布。
- `desktop.draft` 随草案附上版本、SHA-256 和 `specJson`。只有 `desktop.review` 开放审阅操作，它还带复核摘要和有效期。完整规格以审阅事件里的 `specJson` 为准。
- `phone.answer` 关联当前问题事件，`phone.revise`、`phone.confirm`、`phone.reject` 关联当前审阅事件。四种操作都带 `inReplyTo`、`specVersion` 和 `specSha256`。回答与修改请求另带 `text`。`phone.cancel` 通过 `inReplyTo` 取消当前事件对应的回合。
- `desktop.status` 发布排队、运行和终止状态。确认成功状态还带原审阅版本和摘要、确认事件 ID，以及独立的 `savedSpecSha256`。已保存规格的 `status` 改成 `confirmed` 后，需对保存的规格重新计算摘要。`desktop.error` 只发布机器可读的错误码。所有显示文案由客户端映射。

电脑保存阶段 2.1 的 UTF-8 规格 JSON 表示，键排序规则使用 `spec_workflow.py` 的摘要算法。手机直接对 `specJson` 解码后的 UTF-8 字节计算 SHA-256，保留原串供重试和审阅。传输层校验摘要以及草案的项目、版本和 `draft` 状态。完整规格 Schema 及能力审查由确定性规格流程执行。确认事务复核当前版本、原始审阅摘要和完整规格后保存一次并发布 `confirmed`。

## 状态迁移

| 当前状态 | 后续状态 |
| --- | --- |
| `connected` | `queued`、`cancelled`、`failed` |
| `queued` | `running`、`cancelled`、`failed` |
| `running` | `waiting_for_user`、`result_ready`、`cancelled`、`failed` |
| `waiting_for_user` | `queued`、`cancelled`、`failed` |
| `result_ready` | `result_ready`、`queued`、`confirmed`、`cancelled`、`failed` |
| `failed` | `queued`、`cancelled` |
| `confirmed`、`cancelled` | 终态 |

发布草案时保持 `running`，问题进入 `waiting_for_user`，审阅进入 `result_ready`。回答或修改请求使回合重新排队。确认完成后进入 `confirmed`，拒绝或取消进入 `cancelled`。一个项目同一时刻只有一个活动回合。已失败的付费请求需要明确触发新尝试。

审阅过期后拉取会续发审阅事件。当前版本被占用时，确认返回 `SPEC_MISMATCH`，并以新版本续发审阅事件。续发审阅保持 `result_ready`，使用新的事件 ID，仍需用户明确确认。确认通过前置检查后，电脑先持久化确认操作，再原子发布版本，最后提交 `confirmed` 事件。服务重启时恢复未完成的确认操作。详见 [阶段 B.6](../阶段B.6手机审阅与规格确认.md)。

## 认证、分页和重试

- B.3 在配对时固定的 HTTPS 身份上实现 `POST /v1/dialogue/pull`、`/v1/dialogue/ack` 和 `/v1/dialogue/submit`。请求携带 `Authorization: Bearer …` 和 `X-Credential-Id`。电脑校验凭据、设备及会话归属。成功返回 `dialogue.page`、`dialogue.ack` 或 `dialogue.accepted`，业务错误返回 `dialogue.error`。
- `after` 为排他的电脑事件序号，0 表示从头开始。`limit` 为 1–20，`next` 为最后返回的序号，空页沿用 `after`。`hasMore` 为真时至少返回一条。每页事件按序连续，分段还要满足字节上限。手机按序持久应用事件后发送 `through` 确认已处理的连续前缀。电脑幂等保存最大确认位置并返回当前水位。确认只影响传输水位。
- 电脑在事务内先检查事件 ID，再检查下一客户端序号、当前关联事件、有效期、规格摘要和状态。事件 ID、序号和原始 `createdAt` 在重试期间保持稳定。已接受的相同事件返回原 ID 和序号并标记 `duplicate`。同 ID 修改任一字段返回 `EVENT_ID_CONFLICT`，并发提交争用序号返回 `EVENT_SEQUENCE_CONFLICT`。失败的提交不消费序号。后续重试须从电脑最新事件开始判断。新提交的允许时间为电脑时间前 24 小时至未来 5 分钟，问题和审阅在电脑时间到达 `expiresAt` 时过期。
- 按服务端接收时间留存完整协议事件至少 7 天。保留会话终态、确认结果和去重水位作为持久状态。清理后的旧游标返回 `CURSOR_EXPIRED`，越过已发序号返回 `INVALID_CURSOR`。收到过期水位后刷新会话当前状态再继续，不能跳过缺失页后自动确认。已接受但已清理的旧事件以水位拒绝再次提交。
- `STALE_EVENT`、`EXPIRED_EVENT`、`SPEC_MISMATCH` 和 `INVALID_STATE` 需要刷新上下文。传输中断或限流可用原事件退避重试。版本、鉴权、撤销和输入错误按各自错误码处理。传输错误码和模型错误码的全集在 Schema 里。
- `desktop.error` 终止本次模型回合。超时、提供方断连和电脑恢复后的用量不确定状态，由电脑核对费用或由用户明确发起新回合。重复消息、拉取和确认水位沿用原结果。预算、取消和恢复动作见 [阶段 B.7](../阶段B.7预算故障恢复与隐私.md)。

## 大小与验证

信封为严格 UTF-8 JSON 对象，最大 128 KiB，最大 64 层，拒绝重复键、额外字段及非有限数字。草案 JSON 最大 48 KiB。问题和审阅摘要最多 2,000 个 Unicode 码点，回答和修改文本最多 12,000 个码点。序号和规格版本最大为 2,147,483,647。时间为 UTC，最多 6 位小数秒。问题或审阅有效期最长 24 小时。日期、分页一致性、摘要、时序和权限等跨字段约束由运行时校验。

运行 `python scripts/verify-stage-b1.py` 和 `python scripts/verify-stage15.py --serial emulator-5554`。可选使用 `jsonschema[format]` 运行 `python scripts/verify-stage-b1.py --schema` 对 Schema 做独立检查。共享夹具覆盖合法与非法信封、过期、重复、并发冲突、旧协议确认和状态迁移。
